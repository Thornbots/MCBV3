# Pico I2C startup stall investigation — 2026-10-26

## Evidence and limits

Owner's hardware capture of `e85d95f` ran for 323 s: POSE continued, status
was always 2, channel 17 reported `last_seq=0`, both ages `never`, and one
bus reinit. This task did not access the robot. The restored `8d46da5` bus
health was unknown at the time of the brief.

`OdomI2cLog::attempt` is called **after completion**, not before starting a
transaction. Therefore these records cannot distinguish a rejected attach,
a queued/active read that never completes, and an orphaned Busy adapter.
They do not prove that no I2C START was attempted.

## Code findings

The following defects exist in both `8d46da5` and `e85d95f`:

- `MCB-project/taproot/modm/src/modm/platform/i2c/i2c_master_2.cpp`,
  `recoverStuckBus`: clears `::transaction` without calling `detaching`.
  Its caller can then continue startup with interrupts disabled, timing
  registers cleared and the active pointer null. The next refresh resets
  only still-owned transactions; the lost adapter remains Busy forever.
- `callStarting`: after seeing BUSY, recovery ran unconditionally even if
  the short BUSY wait cleared it. If recovery cleared BUSY, it continued
  to generate START despite having discarded its transaction pointer.
- STOP wait loops post-decrement an unsigned counter; exhausting the
  counter wraps it, so the subsequent zero test can miss the timeout.
- `i2c_transaction.hpp`, `I2cTransaction::attaching`: refuses Error as well
  as Busy. Neither Pico nor MT6701 reset this state before retrying.
- `LocalizationPico::run`: both attachment and completion waits are
  unbounded; modm has no general transaction deadline.

The logger changed Pico's transaction type to latch detach errors, added
completion bookkeeping and UART draining, but did not change I2C poll order
(`encoder.run` before `odom.run`), initialization or the two waits. The flag
only reads the last-success clock. Neither introduces a direct scheduling
reason for zero completed reads. Timing/layout changes could expose an
existing startup bus fault; this is not established by the supplied capture.

The strongest explanation for this capture is an orphaned Busy adapter after
startup recovery. Encoder runs first; old `start` still accepts Pico while
reinit is pending, so Pico can start against the disabled/reset peripheral
before the next refresh performs the single reported reinit. An owned first
read waiting forever for an STM32 interrupt also fits. Sticky Error is a
separate retry defect; after a normally recorded failure it cannot by itself
explain `last_seq=0`. The initiating electrical/IRQ condition cannot be
determined from completion-only telemetry. **One deciding observation:** halt the old failing
build once with SWD and capture Pico/MT6701 transaction states, the driver's
active pointer and queue, plus I2C2 CR1/CR2/SR1/SR2 and NVIC enable/pending
bits. Busy with no matching active/queued owner proves orphaning; Error proves
the retry latch; Busy with a matching owner identifies a pending/hung transfer;
Idle with no owner identifies attachment/scheduling instead. Use existing
ELF debug symbols; this observation does not require reflashing.

## Fix and verification boundary

Recovery now detaches active and queued clients before losing ownership,
stops accepting work until reinit, and returns immediately after recovery.
Master reset disables and clears I2C interrupts before changing pointers.
Both clients clear Error before a new poll. Pico attach/completion waits have
a 10 ms deadline; timeout requests shared bus reinit on the next refresh.
The logger records deadline expiry as BusBusy (6) without changing layouts.
POSE is 2 until first success, 0 for successful-read age <50 ms, 2 at >=50 ms.

Five hosted tests execute the real Pico poll: hung first completion, a
startup orphan, rejected first attachment, Error retry, and clock rollover.
All five fail against `e85d95f`'s Pico header. They exercise the driver/client
contract with a fake master, **not STM32 peripheral execution**. Physical
recovery and the 10 ms budget with both real devices still need verification.
The shared-bus recovery also resets MT6701 transactions, so check gimbal
encoder behavior before enabling movement. Persistent bus faults remain 2;
a frozen encoder value with successful reads remains 0.
